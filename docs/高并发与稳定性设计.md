# 云宿数字员工 · 高并发与稳定性设计

> 面向生产部署的架构设计文档。当前交付形态为**单机长连接原型**（飞书 ws client + 内存会话），
> 本文说明其与生产形态的差距，以及向高可用架构的演进路径。
> 更新日期：2026-11-11

## 1. 当前形态与生产形态的差距

| 维度 | 当前原型（P0） | 生产目标 |
|---|---|---|
| 接入 | 单机飞书长连接，进程内事件循环 | 多副本接入层，长连接/ webhook 均可水平扩展 |
| 内核 | 与渠道同进程，同步调用 | 无状态服务，渠道层通过 RPC/HTTP 调用 |
| 会话 | 进程内存字典 | Redis 外置会话（TTL + 序列化） |
| LLM 调用 | 同步阻塞、无超时/重试/熔断 | 异步 IO + 连接池 + 超时/重试/熔断降级 |
| 限流 | 无 | 令牌桶限流（按租户/按渠道） |
| 峰值 | 无削峰手段 | 消息队列削峰填谷 |
| 缓存 | 无（每次全量 BM25） | FAQ 答案缓存 + 检索结果缓存 |
| 成本 | 仅评测期估算 | 实时成本熔断（日预算/单次上限） |

## 2. 核心设计

### 2.1 异步 IO 与连接池
- LLM 调用是主要延迟来源（P95 约 1-3s），必须用异步客户端（`AsyncOpenAI`）+ 共享连接池，
  避免每请求建连；worker 内协程并发处理消息，单机即可支撑数百并发对话。
- 飞书 SDK 事件回调中只做「收消息 → 投递任务 → 立即返回」，业务处理异步化，防止阻塞长连接心跳。

### 2.2 限流（令牌桶）
- 两级限流：**入口限流**（按 chat_id/用户，防单用户刷屏，如 5 msg/10s）与**出口限流**
  （对 DeepSeek API 的全局 QPS + 并发上限，防止打爆配额与账单）。
- `eval/load_test.py` 的信号量 + RateLimiter 即出口限流的最小实现：并发上限 = 信号量，
  QPS 上限 = 令牌桶速率，超出排队等待而非直接拒绝（平滑流量）。

### 2.3 消息队列削峰填谷
- 高并发场景（如门店早高峰集中提问）：接入层把消息写入队列（Redis Stream / RocketMQ），
  内核 worker 按自身处理能力消费，天然削峰；回复通过飞书 API 异步回推。
- 队列长度即背压信号：超过阈值时对新消息降级为「当前咨询较多，请稍候/转人工」，
  而不是无限堆积导致延迟雪崩。

### 2.4 缓存
- **FAQ 答案缓存**：住客 FAQ 类问题（占流量大头）按归一化问题做 key 缓存最终答案
  （如 Redis，TTL 1h），命中即返回，零模型调用。配合知识库版本号失效。
- **检索缓存**：query → top-k 结果缓存（语料静态，TTL 可长）；语料变更时随版本号整体失效。
- 注意缓存只对「确定性答案」生效；涉及会话状态（澄清/重复检测）的请求不得走缓存。

### 2.5 无状态内核 + 会话外置
- 内核 `handle(user_type, text, session)` 本身无状态，会话对象是唯一状态载体。
  把 `SessionStore` 从内存字典换成 Redis（key=`chat_id:user_id`，JSON 序列化，TTL 如 30min），
  内核即可任意水平扩展、滚动发布不丢会话。
- 澄清轮次、重复问题计数等规则依赖会话，外置后语义不变。

### 2.6 水平扩展与背压
- 无状态后按 CPU/队列深度 HPA 扩缩容；检索（BM25 全内存）随实例复制，语料量级无需分片。
- 背压链路：队列深度 → worker 消费速率 → LLM 出口限流。任何一环饱和都应向上游传递
  「慢下来」的信号（队列积压 → 入口降级话术），而不是 OOM 或超时风暴。

### 2.7 熔断与降级
- **模型超时**：单次 LLM 调用超时（如 8s）→ 重试 1 次 → 仍失败则降级：
  有检索结果则返回「规则拼装答案 + 来源」，否则固定拒答话术。绝不让用户等超 5s 首响（SLA 约束）。
- **模型故障熔断**：错误率超阈值（如 1min 内 50%）→ 熔断器打开 30s，期间全部走
  「检索直出 / 拒答兜底」，半开后试探恢复。红线/转人工等确定性规则不依赖模型，始终可用。
- **成本熔断**：单次对话 token 超预算（如 0.10 元对应量级）→ 提前终止 agent loop 并回落；
  日累计成本超预算 → 全局降级为「检索直出 + 高频转人工」，并告警。

## 3. 演进路径

1. **P0（当前）**：单机长连接 + 内存会话 + 同步调用。验证对话逻辑与评测体系。
2. **P1**：内核拆为独立服务（FastAPI），会话外置 Redis；LLM 调用异步化 + 超时/重试；
   加入口限流与 FAQ 缓存。
3. **P2**：引入消息队列削峰、熔断降级、成本熔断；接入层多副本；按队列深度自动扩缩容。
4. **持续**：每次模型/知识库变更 → `run_eval.py` 全量回归（含安全对抗 suite）→
   `load_test.py` 基准复测 → 达标方可发布。

## 4. 当前负载基线（mock，2026-11-11）

`python eval/load_test.py --concurrency 50 --requests 500`（MockLLM，本机）：

- 吞吐量约 **6600 req/s**，延迟 P50 0.2ms / P95 0.4ms / P99 0.5ms，错误率 0%。
- 该数字只代表**规则层 + 检索层的框架开销**；真实部署的吞吐与延迟由 LLM 调用决定，
  需要按 2.1-2.7 的设计保护模型配额与首响 SLA。
